# dachpedigrees — база родословных такс

Переписывание легаси-проекта `dachpedigrees.com` с Drupal 6 на Django + Postgres
с островной интеграцией React.

## Что это за проект

База данных такс с родословными, фотографиями и сопутствующей информацией.
Наполнялась годами, ~50 000 собак. Данные редактируют как владельцы проекта,
так и заводчики через личные кабинеты.

Посещаемость сейчас невысокая, её планируется наращивать.

## Откуда переезжаем

- **Легаси:** Drupal 6 + MySQL. Сайт закрыт HTTP-авторизацией (отдаёт `401`).
- **Особенности Drupal 6, которые ждут в ETL:**
  - поля хранятся в CCK-таблицах `content_field_*` / `content_type_*`,
    а не в `node__field_*` (это Drupal 8+) и не в `field_data_field_*` (это Drupal 7);
  - пароли пользователей — **голый MD5** без соли (в D7+ уже phpass `$S$`);
  - вероятна каша с кодировками latin1/utf8 в дампе;
  - псевдонимы URL лежат в `url_alias` — понадобятся для редиректов и сохранения SEO.

### Принципы миграции

1. **Схема проектируется заново**, а не переносится один в один.
2. **ETL идемпотентен** — рассчитан на десятки прогонов подряд.
3. В каждой таблице хранится **`legacy_id`** — для сверки и редиректов со старых URL.
4. **Учётные записи заводчиков сохраняются.** Django подключает кастомный хешер,
   проверяющий старый MD5-хеш Drupal, и молча перехеширует пароль в свой формат
   при первом успешном входе. Аккаунты и вклад заводчиков — актив проекта.
5. Данные грязные: дубли собак, разная транслитерация кличек, циклы в предках,
   неизвестные родители, даты в свободной форме. Схема обязана это переживать,
   а ETL — отчитываться о том, что не сошлось.

## Стек

| Слой | Решение |
|---|---|
| Бэкенд | Django 5.2, Python 3.13 |
| БД | PostgreSQL 17, локаль `C.UTF-8` |
| Фронтенд | React + TypeScript + Vite, **островами** внутри шаблонов Django |
| Очереди | Celery + Redis |
| Прод | nginx + gunicorn, всё в Docker |

Django рендерит страницы и держит SEO; React живёт только там, где нужна
интерактивность — дерево родословной, фильтры поиска, загрузка фото.

### Почему острова, а не SPA

Справочник живёт за счёт поискового трафика. Серверный рендер обязателен,
а интерактивность нужна точечно. Отдельный SPA + DRF здесь дал бы вдвое больше
кода и проблему с индексацией на ровном месте.

## Устройство репозитория

```
backend/
  config/settings/{base,dev,prod}.py   расщеплённые настройки
  config/celery.py
  apps/core/                           health-check, базовые шаблоны
    templatetags/islands.py            тег {% island %} — точка монтирования
  apps/pedigree/                       модели собак (в работе)
  templates/                           base.html + шаблоны приложений
  frontend_dist/                       сюда Vite кладёт бандл и манифест
  Dockerfile                           двухстадийный: node собирает → python забирает
frontend/
  src/registry.ts                      реестр островов (имя → ленивый импорт)
  src/main.tsx                         сканирует DOM, монтирует по data-атрибутам
  src/islands/<Name>/index.tsx
  vite.config.ts                       пишет результат в ../backend/frontend_dist
docker/initdb/01-extensions.sql        pg_trgm, unaccent
nginx/default.conf
docker-compose.yml                     разработка: runserver + Vite с HMR
docker-compose.prod.yml                прод: nginx + gunicorn + celery worker/beat
```

### Как работают острова

1. В шаблоне Django ставится `{% island "DemoSearch" props=... %}` —
   тег рендерит `<div data-island="DemoSearch" data-props="{...}">`.
2. `main.tsx` при загрузке обходит все `[data-island]`, берёт компонент
   из `registry.ts` и монтирует его, передавая распарсенный `data-props`.
3. Каждый остров попадает в свой чанк — страницы не тянут лишний JS.

Добавление острова: компонент в `src/islands/<Name>/index.tsx`, строка
в `registry.ts`, вызов тега в шаблоне. Больше ничего.

## Модель данных: ключевые решения

- **Родословная — граф.** Предки и потомки достаются рекурсивными CTE Postgres.
  На 50 000 собак этого достаточно, closure-таблица не нужна.
  Пересматривать при кратном росте базы.
- **COI (коэффициент инбридинга)** считается по 10 поколениям ночной задачей
  Celery и складывается в отдельную таблицу с отметкой времени расчёта,
  процентом известных предков и ancestor loss. На лету не считать.
- **Разновидности таксы** — комбинация размера (standard / miniature / rabbit)
  и типа шерсти (smooth / long / wire). Проект однопородный, и это преимущество:
  можно уходить вглубь там, где универсальные движки не могут.
- **Регистрационных номеров у собаки может быть несколько** — разные кинологические
  организации разных стран.
- **Здоровье — отдельная сущность и главный дифференциатор** (см. ниже).

## Конкурент

`dachshund.breedpedigree.com` — движок «на все породы», натянутый на такс.
Частично скопировал нашу базу.

**Что у них есть:** 491 761 собака; COI за 10 поколений с ancestor loss и временем
пересчёта; дерево 3/4/5 поколений с пометкой общих предков (`×2` с номером);
титулы с привязкой к стране; помёты, однопомётники, потомство; пробная вязка
(test mating); журнал изменений; правки и загрузка фото пользователями;
SSO на отдельном домене; мультиязычность; SEO-раздел со статьями.
Полнота родословных: 3 поколения — 59%, 4 — 44%, 5 — 24%.

**Где они уязвимы — туда и бьём:**

1. **Здоровья нет вообще.** Для таксы это главная тема: IVDD (дископатия),
   болезнь Лафоры у жесткошёрстных кроличьих, cord1/PRA, вывих коленной чашечки.
   Заводчик подбирает пару по риску, а не по красоте. База генотипов носителей
   плюс подсветка опасных сочетаний в пробной вязке — то, за чем пойдут к нам.
2. **Качество данных.** Скрейп означает дубли и мусор. Наш козырь —
   верифицированные записи со ссылкой на источник и сканами документов.
   50 тысяч чистых записей бьют полмиллиона грязных, если разница видна.
3. **География.** В их фильтрах нет США, Великобритании, Украины, Чехии, Франции.
   Если база сильна по России и Восточной Европе — там мы плотнее.

Сверх их функционала: коэффициент родства между двумя конкретными собаками,
AVK, генетическое разнообразие по питомнику.

## Развёртывание

Целевая машина — VPS. Локальная разработка на Windows через WSL2 была
свёрнута: TLS-инспекция в сети ломала загрузки, а служба `LxssManager`
зависла в `StopPending`. Работаем прямо на сервере.

Проект живёт в `/home/bob/dogs/`.

## Договорённости по стилю работы

- Комментарии и документация — **на русском**, код и идентификаторы — на английском.
- Порты Postgres и Redis публикуются только на `127.0.0.1`, наружу не торчат.
- Node в рантайме отсутствует: фронтенд собирается первой стадией Dockerfile.
- Контейнеры не работают от root — в образе заведён пользователь `app` (uid 1000).
- Оформление шаблонов намеренно минимально: визуальное решение делает
  отдельный человек, не занимать это место заглушками.

### Безопасность: важное

Порты **всех** сервисов привязаны к `127.0.0.1`. Изначально `backend` (8000)
и `frontend` (5173) висели на `0.0.0.0` и были открыты в интернет при
`DEBUG = True` и `ALLOWED_HOSTS = [*]` — то есть страница ошибки Django
отдавала бы настройки и пароль Postgres любому сканеру. Исправлено.

**Не публиковать порты наружу.** Доступ к стенду — только через SSH-туннель:

```
ssh -L 8000:localhost:8000 -L 5173:localhost:5173 dachs-vps -N
```

Прочее, что ещё не сделано: файрвол (`ufw`) неактивен; парольный вход по SSH
не отключён; `bob` имеет sudo без пароля. Перед продакшном закрыть всё три.
